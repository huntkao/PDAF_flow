生命週期狀態機：何時真的量測，何時只是等待

七個 AfState 中，只有兩個會呼叫 disparity search（M1 SAD cost + M2 拋物線內插）； 其餘都是控制鏡頭移動時序與收斂判斷的簿記狀態。這個區分，就是「frame 3 是否還沒到位」與 「frame 4 誤差反而較大」兩個疑問的根源。

狀態機是 disparity search 系統的核心嗎？

不是同一層。狀態機是「排程 / 控制層」，disparity search 是它有條件呼叫的「運算層」。

分層

AfController::onFrame() 的 switch-case 本身不含任何 SAD 匹配或拋物線內插邏輯—— 它只決定「這一 frame 要不要呼叫 handleMeasurement()」。真正的 disparity search （M1 + M2）被封裝在 IFocusEstimator::process() 裡，由 handleMeasurement() 呼叫。

而 handleMeasurement() 只在 kMeasuring 與 kVerifying 這兩個 case 被呼叫。kMoving / kSettling 純粹等待 actuator 到位， 不產生任何量測——這正是 frame 3 的 disparity/confidence 顯示為 0 的原因。

控制層 — AfController FSM（排程 / 收斂判斷）
IDLE MEASURING MOVING SETTLING VERIFYING FOCUSED FAILED
運算層 — Disparity Search（僅被綠色 pill 呼叫）
M1 SadCostEngine（LRC + SAD） → M2 ParabolicDepthEstimator（cost-min + 拋物線次像素）

狀態轉移圖

實心填色 = 該 frame 實際跑了 disparity search；空心外框 = 純等待、無量測。上方軌道通往 FOCUSED，下方軌道通往 FAILED。

MEASURING / VERIFYING — 執行 M1+M2 IDLE / MOVING / SETTLING — 等待，無量測 FOCUSED — 終止（成功） FAILED — 終止（失敗，虛線外框）

邊界行為測試 — in_focus_disparity / max_iterations

以 mid 情境（config/default.json，f0 disparity=-2.497）為基準，只改動單一 tuning 參數，觀察狀態機在邊界值上的行為。

結論

容忍區(in_focus_disparity)太鬆：狀態機會把明顯還沒對到焦的畫面直接判 FOCUSED，鏡頭從未移動——這是調參時真正的風險，容忍區必須小於系統實際能達到的殘差量級，而不是「數值看起來合理」就好。

容忍區太緊：撞到的是感測雜訊 / 量化底噪（約 0.001–0.01 disparity 量級），不是演算法收斂不了——這條邊界揭示的是硬體精度極限，調更多次迭代也無法突破。

max_iterations 的安全值是情境相關的：mid 情境剛好只需要 1 次移動即可收斂，=0 會直接失敗、=1 剛好夠——這條分界線在其他情境（例如 far）下會不同。

邊界行為測試 — confidence_threshold × max_retries

同樣以 mid 情境為基準（f0 disparity=-2.497，理論 confidence≈0.690±0.01 的雜訊帶）。 這組參數與前一組不同：in_focus_disparity/max_iterations 決定「移動幾次」， 這組決定的是「每次量測要不要相信」。

結論

門檻比較是嚴格小於（conf < threshold）：threshold 剛好等於當次 confidence 時視為通過，不會誤觸重試——這是精確的邊界，不是「差不多」。

threshold 落在 confidence 雜訊帶內時，重試變成賭運氣：同一顆鏡頭位置反覆量測，靠 RNG 雜訊讓某一次剛好跨過門檻，成功但多花幾個 frame，而且最終收斂到的 lens_step 會因為「用哪一次量到的 disparity」而有些微差異（174 vs 175）。

max_retries 是硬上限，不保証機率：FAILED 固定發生在第 max_retries+2 次量測（第 1 次 + max_retries 次重試後再判一次）。但如果 threshold 高於這個情境 confidence 分布的天花板，重試預算再大也沒用——賭桌本身就贏不了。

邊界行為測試 — shift_min / shift_max 搜尋窗邊界

這組參數不歸 AfController 管，是 M1/M2 的搜尋範圍：cost engine 只在 [shift_min, shift_max] 內取樣，M2 的谷底若落在窗口最邊緣（mi==0 或 mi==n-1），會觸發 parabolic_depth_estimator.cpp 裡的 boundary 分支：不做拋物線內插、confidence 直接打對折。

結論

窗口小於真實 disparity 不會讓系統壞掉，但會被 clamp 在窗緣、confidence 對折：估測值不是真值，只是「已知在這個方向、但至少這麼遠」，系統靠後續 iteration 自我修正，多花幾個 frame 才收斂到位。

CLAUDE.md 標註的 aliasing 安全邊界（頻率 < π/max_shift）比實測門檻保守：實測把窗口從 ±16 一路擴到 ±48（遠超安全邊界），cost curve 都只有單一極小值，沒有觀察到假極小值——原因是模擬器的離焦模糊半徑（radius=min(6, defocus/25)）在大位移時同時放大，高頻紋理被模糊掉，間接降低了 aliasing 風險。這是這個模擬器的隱含保護，不代表任意搜尋窗在真實系統上都安全。

confidence 不是窗口大小不變量：窗口越寬，confidence 單調上升（0.690→0.717，見下表），但這不是量測變準——是 depth = 1 - cmin/mean 裡的 mean 被更多不匹配樣本拉高、虛高了 confidence。調 shift_min/max 與調 confidence_threshold 必須一起看，不能獨立設定。

48{
49  AfFrameLog log;
50  log.frame_id = input.meta.frame_id;
51  log.state_before = state_;
52  log.lens_step = actuator_.getStatus().current_step;

54

56  {
57  case AfState::kIdle:
58  case AfState::kFocused:

71  case AfState::kVerifying:

74  }
